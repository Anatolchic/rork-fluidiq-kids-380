# Rate-limit правила Репетиторов

Плагин: [`mholt/caddy-ratelimit`](https://github.com/mholt/caddy-ratelimit).
Хранилище счётчиков: in-memory (на один инстанс Caddy — нам достаточно).
Ключ окна: IP клиента (`{http.request.remote.host}`), Caddy уже видит реальный IP
потому что сидит на edge (Beget без CF-проксирования).

Ответ при превышении: HTTP `429 Too Many Requests` + заголовок `Retry-After`.

---

## Зона `auth_brute` — защита от подбора паролей и OTP

| Параметр | Значение |
|---|---|
| Endpoints | `/auth/v1/token`, `/auth/v1/signup`, `/auth/v1/recover`, `/auth/v1/otp`, `/auth/v1/verify`, `/auth/v1/magiclink` |
| Лимит | **5 запросов / минуту / IP** |
| Window | 1 минута (sliding) |

### От чего защищает

- **Brute-force паролей** (`/auth/v1/token?grant_type=password`) — 5 попыток/мин
  на IP делает перебор бессмысленным. Supabase сам ещё умеет lockout, но это
  второй слой.
- **OTP-флуд** (`/auth/v1/otp`, `/auth/v1/magiclink`) — без лимита злоумышленник
  может слать SMS/email на чужие номера, выжигая нам бюджет провайдера и
  досаждая жертве. 5/мин — нормальный пользователь столько никогда не нажмёт.
- **Account enumeration** через `/auth/v1/recover` (узнать какие email
  зарегистрированы по разнице в ответе/тайминге).
- **Signup-флуд** — массовое создание фейковых аккаунтов.

### Почему не глобально 5/мин на весь `/auth/v1/*`

Endpoints `/auth/v1/user`, `/auth/v1/logout`, `/auth/v1/session` вызываются
легитимно часто (refresh токенов в фоне). Их сюда не включаем.

## Зона `rpc` — защита бизнес-логики

| Параметр | Значение |
|---|---|
| Endpoints | `/rest/v1/rpc/*` (все Postgres-функции через PostgREST) |
| Лимит | **60 запросов / минуту / IP** |
| Window | 1 минута |

### От чего защищает

- **Абуз дорогих RPC** (расчёт биллинга партнёра, генерация PDF-отчётов,
  агрегации по большому окну дат) — одиночные запросы тяжёлые, 60/мин — выше
  любого нормального UX-паттерна.
- **Скрапинг через RPC** — если кто-то решил вытащить весь каталог репетиторов
  через свой эндпоинт `search_tutors()`.
- **Application-layer DoS** — RPC дороже чем простой `SELECT` через REST,
  поэтому отдельный лимит.

### Почему 60, а не 30

Реальные пользователи иногда жмут «обновить» в чате/календаре, и каждое
действие может стрелять 2-3 RPC. 60/мин = 1/сек в среднем — комфортно для UX,
жёстко для бота.

---

## Что НЕ покрыто rate-limit (намеренно)

| Endpoint | Почему без лимита |
|---|---|
| `/rest/v1/<table>` | RLS + JWT защищают от чужих данных. Скрапинг детектится по логам, не лимитом. |
| `/storage/v1/*` | Бакеты приватные, доступ по подписанным URL. |
| `/realtime/v1/*` | WebSocket, лимит на коннекты лучше делать в Realtime-сервисе. |
| `/functions/v1/*` | Edge Functions сами решают свои лимиты (особенно сheduler с `x-cron-secret`). |
| Лендинг `repetitory-app.ru` | Статика, отдаётся файл-сервером, мизерная нагрузка. |

## Мониторинг

В логах `/var/log/caddy/supabase.log` (JSON-формат) ищем строки с
`"status": 429`:

```bash
sudo tail -f /var/log/caddy/supabase.log | jq 'select(.status == 429) | {ts, ip: .request.remote_ip, uri: .request.uri}'
```

Если в день > 100 событий 429 с одного IP — кандидат на бан через
`ufw deny from <IP>` (обсудить с владельцем перед действием — слёзное правило
про файрвол).

---

## Когда пересматривать лимиты

- Релиз новой фичи которая легитимно генерит много RPC → проверить логи
  на ложные 429 первую неделю.
- Подключение партнёра с собственным backend (server-to-server) → дать ему
  отдельный домен/ключ и whitelist по IP в отдельной зоне.
- Жалоба пользователя «не могу залогиниться» → проверить не уткнулся ли
  в `auth_brute` (бывает при тестировании с одного IP всей команды).
